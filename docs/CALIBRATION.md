## 1. 切视频：靠滚轮还是方向键？几格才稳？

### 做了什么实验

在「推荐」feed 上（左侧导航高亮带 = y 116..155，即"推荐"被选中，确认在 feed 页），光标放在视频区中心，
逐个注入下面的动作，每次注入后等 1.3s 再截图。判据是**标题文字高亮掩码指纹**：
取底部左侧的「@作者 · 日期 / 标题 / #话题」区域（客户区 168..760 × 745..852），只统计"高亮(luma>205)且低饱和"的
白色文字像素，按 24×5 网格计数成向量再比 L1 距离。视频画面在动、文字是静态的，所以这个指纹对"画面在动"免疫。

对照组：同样的间隔**不发任何注入**。

| 注入 | 指纹距离（vs 原视频） | 是否换视频 |
| --- | --- | --- |
| 对照组（不注入，隔 1.4s） | 0.8 | 否（≈0，指纹稳定） |
| wheel(-1)（1 格） | 47.9 | **是** |
| wheel(+1)（回滚） | 4.8 | 回到原视频 |
| wheel(-3)（3 格） | 45.7 | **是**（落在同一条"下一条"上） |
| wheel(+3) | 4.8 | 回到原视频 |
| ArrowDown | 46.5 | **是**（同上，同一条） |
| ArrowUp | 4.8 | 回到原视频 |

标题条逐帧裁剪拼图肉眼复核：原视频是「@沸腾哥象棋」；wheel(-1) / wheel(-3) / ArrowDown 三次都落到同一条
「@不会捏蓝(东东电竞)」；wheel(+1) / wheel(+3) / ArrowUp 三次都精确回到「@沸腾哥象棋」。

### 观察到什么

1. **滚轮与方向键都能切视频**，效果完全等价（都恰好走 1 条）。
2. **步长由"事件个数"决定，不由 zDelta 决定**：一次事件 zDelta=±120（1 格）与 ±360（3 格）都只切 1 条。
   所以 SwipeConfig.notches 取 1；如果注入器把 notches 拆成多次事件发，取 3 就会一次跳 3 条。
3. **方向**：负向（滚轮朝下）切到"没看过的新视频"，正向（朝上）精确回到"刚才那条"；
   过渡动画帧显示旧内容从上方退出、新内容自下方进入 —— 这就是抖音纵向 feed 的"下一条"语义。
   即 **负 = 下一条（swipe_down），正 = 上一条（swipe_up）**。
4. **滚轮作用点有限制**（对集成很关键）：

| 光标位置（客户区归一化） | 结果 |
| --- | --- |
| 视频区中心 (0.5, 0.5) | 换视频 ✓ |
| 底部进度条上方 (0.5, 0.97) | 换视频 ✓ |
| 右侧按钮栏 (0.9685, 0.55) | 换视频 ✓（按钮栏在播放容器内，滚轮照常落到容器） |
| 左侧导航栏 (0.05, 0.5) | **不换**（被导航栏自己的滚动区吞掉） |

### 结论

* swipe.method = "wheel"，**notches = 1**；wheel(+1) = 上一条，wheel(-1) = 下一条。
* 备选 method = "key" + key_down="down" / key_up="up"，实测效果一模一样（同样要求抖音在前台）。
* **douyin.py 因此在发滚轮前会先把光标挪进视频区**（仅当光标落在左侧导航/窗口外时才挪，滚完还原），
  否则用户用右摇杆把光标停在侧栏时，切视频会静默失效。
* 二次确认：wheel(-1)、ArrowDown 各做 2 次，落点一致。

## 2. 点赞：双击视频区，落点选哪

### 做了什么实验

**没有真点。** 按安全约束（不刷数据、不污染账号），本项用 UI 位置推断 + 区域排除法：

1. 抓 feed 帧，标出所有可点控件的归一化位置：左侧导航 0.00–0.10；右侧竖排按钮栏 0.94–0.99
   （心形/评论/收藏/分享/听抖音/更多，质心实测见第 3 节）；底部播放控制条 y>0.94（进度条、弹幕输入框、清晰/倍速/音量）。
2. 播放区内部（x 0.10–0.94、y 0.13–0.93）没有按钮/滑块/输入框，双击不会误触 UI。
3. 抖音"双击视频 = 点赞"是客户端内建手势，只要落点在播放容器内即可。

### 观察到什么

* 视频区中部（如 0.5 / 0.45）四周 300px 内没有任何控件；单击 = 播放/暂停，双击 = 点赞。
* 因为单击是"暂停"，点赞**必须用双击**（用两次间隔很短的 click_normalized 也可以，但双击更符合原生意图）。

### 结论

* like.method = "double_click"，x = 0.5，y = 0.45（客户区 825, 417）。
* **诚实声明**：本条是"UI 位置推断 + 安全约束"的结论，**未做真实双击**（避免给用户账号刷一个赞）。
  若真机发现双击不点赞，改配置即可切到"点右侧心形"：{"method": "click", "x": 0.9685, "y": 0.5124}
  （心形质心实测坐标，见第 3 节）。douyin.py 两种 method 都支持，切配置不用改代码。

## 4. 返回：Esc 还是 alt+left？

### 做了什么实验

用"页面状态探针"逐状态试键。探针 = 左侧导航栏（客户区 x 12..148）逐行亮度剖面里找**被选中的高亮带**
（选中项有浅色圆角底）。实测高亮带与导航项逐个点击核对过：「推荐」= y 116..155、「我的」= y 307..346、
「放映厅」= y 414..453、「短剧」= y 456..495，判据可靠。

| 场景 | 操作 | 观察 | 结果 |
| --- | --- | --- | --- |
| 推荐 feed | Esc | 高亮带不变 (116,155)；版面差异 2.0（≈0） | **无反应** |
| 推荐 feed | alt+left | 版面差异 1.6 | **无反应** |
| 评论抽屉打开 | Esc | 心形列仍 1179.5（抽屉没关）；版面差异 0.4 | **关不掉** |
| 评论抽屉打开 | 先点进抽屉再 Esc | 仍 1179.5 | **关不掉** |
| 评论抽屉打开 | alt+left | 版面差异 20.9 / 153 格变化，页面确实变了 | 有反应（疑似历史后退），不稳定 |
| 一级页「我的」 | Esc / alt+left | 高亮带始终 (307,346) | **都无反应** |
| 一级页「放映厅」 | Esc | 高亮带始终 (414,453) | **无反应** |
| 短剧详情页（点卡片进入） | Esc / alt+left | 版面差异 19.8 / 25.2（都不是"回到短剧列表"的 59.8） | **都没回上一级** |
| 清晰度下拉菜单弹出 | Esc | 菜单消失（下一帧已无下拉层） | **能关弹出层** ✓ |

### 观察到什么

* Esc：唯一确证有效的是**关闭弹出层**（清晰度菜单）；对抽屉、一级页、详情页都无效。
* alt+left：多数状态无效；只在"feed + 抽屉打开"那一次观察到页面变化（疑似应用内历史后退），重试不稳定。
* 这个客户端里**没有哪个键是稳定的"返回"**。真正可靠的返回是点 UI：
  抽屉右上角 × (0.9830, 0.0863)、抽屉态评论图标 (0.7145, 0.5922)、左侧「推荐」导航 (0.0515, 0.1435)。

### 结论

* 默认 back.method = "key"，**back.key = "esc|alt+left"**（按顺序发：先 Esc 关弹出层，再 alt+left 试历史后退）。
  依据：两者在首页 feed 上**都是空操作**（版面差异 ≤2，不会把用户带到别处），串起来发是安全的；
  而在"有弹出层 / 有历史"的状态下至少有一个能命中。
* 备选一：只用 esc（最保守，只关弹出层）。
* 备选二：真要"返回上一级"就用点击 —— {"method": "click", "x": 0.9830, "y": 0.0863}（关评论抽屉）
  或 (0.0515, 0.1435)（回首页推荐流）。实测这两种确实生效，但只对特定页面成立，当默认会在一级页上误触导航。
* 未验证项：搜索结果页 → 返回（按安全约束不做搜索，故没测）。

## 5. tools/measure.py --report（复校工具）

用途：客户端改版 / 换分辨率 / 换显示器后重新量坐标，或排查"点了没反应"。

    python tools/measure.py --report                     # 客户区矩形 + 各动作归一化->绝对像素
    python tools/measure.py --report --shot --crosshair   # 存 %TEMP% 截图并画出各 click 动作的十字准星
    python tools/measure.py --report --shot --printwindow # 窗口被遮挡时用 PrintWindow 抓真实内容
    python tools/measure.py --x 0.9685 --y 0.5922         # 单点换算
    python tools/measure.py --report --mark 0.9685,0.6753 # 额外标记点，方便量新图标

实测输出（本机，见验收记录）：客户区矩形、DPI 模式、每个动作的归一化坐标与换算后的绝对像素、当前切视频配置。

注意事项：

* 工具自己声明 DPI 感知（per-monitor-v2），否则拿到的是被缩放过的虚拟坐标。
* 截图默认落 %TEMP%，不进仓库；docs/*.png 也已在 .gitignore 里。
* 只有**普通视频 feed + 评论抽屉关闭**时这套坐标才成立；直播房间、抽屉打开态、全屏播放时按钮栏位置不同。

## 7. 已知风险（给集成方）

1. **左侧导航栏会吞掉滚轮**：光标停在 x<0.10 时滚轮不切视频。douyin.py 已自动把光标挪进视频区再滚（滚完还原）。
2. **直播房间右侧 UI ≠ 普通视频**：feed 会插播直播，此时 0.9685 落点不是"收藏/评论"。
   动作层无法在不截图的情况下区分，属已知限制；要严格可在 app 层加画面特征判定。
3. **评论抽屉打开时按钮栏左移 419px**：此时按 0.9685 会点到抽屉内容。
4. **键盘动作要求抖音在前台**：Esc/方向键发给当前前台窗口；滚轮发给光标下的窗口。
5. **实测期间存在外部注入干扰**（见第 0 节）。切视频、返回键结论在"无外部注入"的重跑中复现一致，故成立；
   点赞一项额外保守（未真点）。
6. xbox_douyin/config.py 里四个动作目前仍是占位 (0.5, 0.5)（本 teammate 无权改该文件）。
   douyin.py 因此带了一层保护：检测到配置仍是占位 (0.5, 0.5) 时改用上表实测值并打 debug 日志。
   Lead 把上表写进 config.py 默认值后，这层保护自然失效（配置优先）。

## 8. 快进 / 倍速实测（追加，2026-01 第二轮）

> 编号说明：Lead 要求的标题是"第 6 节"，但文件里 6/7 已被占用（校准值总表、已知风险），
> 为不改动已有小节号，本轮追加为第 8 节。

同一台机器、同一个抖音客户端（客户区 1651×928，普通视频 feed）。判据统一为**左下角时间码**
（客户区 (205,872)-(310,906)，"00:42 / 08:59" 格式）：注入前后各截一张图，直接读秒数差，
比"画面差异"干净得多。控制组（同间隔零注入）在 1x 下每 1.3s 约 +1~2s，作为基线。

### 8.1 ←/→ 能不能 seek？步长几秒？

**做了什么**：分别在"播放中"和"暂停"两种状态，单次按 ← / → 各 3 次、Shift+← / Shift+→ 各 2~3 次，
每次按下后 0.5~1.5s 读时间码；播放态基线由"对照组"给出（1.3s ≈ +1~2s）。

**观察到什么**（播放态，1.5s 间隔，节选）：

| 动作 | 时间码 | 相对上一行 | 解释 |
| --- | --- | --- | --- |
| 对照组（不按） | 01:13 → 01:15 | +2 | 1x 正常播放 |
| → #1 | 01:16 | +1 | 只有播放推进 |
| → #2 | 01:18 | +2 | 只有播放推进 |
| → #3 | 01:19 | +1 | 只有播放推进 |
| ← #1 | 01:16 | **-3** | -5s seek + 1.5s 播放 |
| ← #2 | 01:12 | **-4** | -5s seek |
| ← #3 | 01:09 | **-3** | -5s seek |
| Shift+→ #1/#2 | 01:10 / 01:12 | +1 / +2 | 无 seek |
| Shift+← #1 | 01:09 | **-3** | -5s seek |
| Shift+← #2 | 01:05 | **-4** | -5s seek |

暂停态（时间码自身不推进，更干净）同样复现：← 每次 -5s，→ 从不变化。

**结论**：
* **← 与 Shift+← 都等于"后退 5 秒"**（多次复现，7 次以上）。
* **→ 与 Shift+→ 没有任何 seek 行为**（10 次以上，播放态/暂停态都试过，净变化始终等于播放基线）。
* 即：客户端只实现了"后退"，**没有键盘快进**。RB 想要"前进几秒"不能靠键盘。

### 8.2 长按是连续 seek 还是只走一步？

**做了什么**：按住 ← 1000ms 再松开（两次），与单次 ← 对比；按住 → 1000ms 一次。

**观察到什么**：

| 动作 | 时间码 | 相对上一行 |
| --- | --- | --- |
| ← 单次（参考） | 01:02 | -4（= -5s seek + 1s 播放） |
| ← 单次（参考2） | 00:58 | -4 |
| ← 按住 1000ms | 00:55 | **-3（仍只有一步）** |
| ← 再按住 1000ms | 00:51 | **-4（仍只有一步）** |
| → 按住 1000ms | 01:08 | +3（纯播放，无 seek） |

**结论**：长按**不会连续 seek**，按住 1 秒与单击一次的位移相同（播放器没吃 Windows 的按键自动重复）。
"按住 → 连续快退"这条路不存在。

### 8.3 有没有别的 seek 快捷键？

**做了什么**：逐个按 J、L、逗号、句号、PgUp、PgDn、Shift+逗号、Shift+句号、=（等号）、-（减号）、
[、]、Shift+[、Ctrl+[、x、Shift+x、Ctrl+x、Shift+=、Alt+x、Home，每次读时间码/速率标签。

**观察到什么**：**全部无反应**（时间码只按播放推进；速率标签始终 1.0x）。
唯一有效的是 8.1 里的 ← / Shift+←。

**结论**：客户端没有别的 seek 或倍速快捷键；seek 只有"后退 5 秒"一种键盘入口。

### 8.4 「倍速」按钮与菜单

**做了什么**：点底部控制条右侧「倍速」文字，抓图并 4 倍放大读每一项的像素位置；选 2.0x 后用
"两次相隔 3s 的时间码"验证速率；再切回 1.0x 复测。

**观察到什么**：

* 点开后弹出**竖直菜单**（在按钮上方），7 档，当前档位有浅色高亮底：

| 档位 | 客户区 y | 归一化 y |

| 0.75x | 632 | 0.6817 |

### 8.5 恢复 1x 的可靠路径

**做了什么**：按 8.4 的坐标点「倍速」→ 点菜单 1.0x；实测后复测速率与标签。

**观察到什么**：点完标签回到 **1.0x**，速率实测 +3s/3.3s＝1x；之后换视频仍是 1x（连抓 4 条视频的底部条，
普通视频全部显示 1.0x）。

**结论**（操作序列）：
1. 点 (0.8600, 0.9633) 打开倍速菜单（**光标要停在这个按钮上**）；
2. 立刻点 (0.8618, 0.7195) 选 1.0x；两次点击之间**绝对不能移动光标到别处**，否则菜单关闭、
   第二次点击会落在视频画面上（= 播放/暂停，会误暂停）。
3. 校验：底部条右侧标签应显示 1.0x。

### 8.6 长按视频区有没有原生倍速？

**做了什么**：鼠标左键按住视频区 (0.35, 0.55) 1.2 秒，按住中与松开后各读一次时间码。

**观察到什么**：00:56 → 00:57（按住 1.2s 后）→ 00:58（松开 0.5s 后），推进速率始终是 1x，
画面没有出现"倍速中"提示。

**结论**：**PC 端没有手机 APP 那种"长按倍速"手势**。想倍速只能点菜单。

### 8.7 直播房间有没有倍速？

**做了什么**：连续切视频，抓每一条的底部控制条（x 1150..1651, y 862..918），对比普通视频与直播房间。

**观察到什么**：
* 普通视频底部条：时间码 + 弹幕框 + 「连播 清屏 智能 倍速/1.0x」+ 菜单/画中画/音量/小窗/全屏。

**结论**：倍速按钮只在普通视频上存在。在直播房间里点 (0.8600, 0.9633) 会打到别的控件（附近是 连播 开关/音量），

### 8.9 本轮风险

1. **菜单是 hover 层**：两次点击必须连发且不移动光标，否则第二次点击落到视频上会误触播放/暂停。
2. **直播房间没有倍速按钮**：动作层无截图能力 → 无法自判，只能在契约/调用侧保证"仅普通视频"。
3. **坐标依赖版面**：普通 feed 底部条与"视频详情页"底部条位置不同（详情页底部条在客户区 y≈261），
   同一套归一化坐标不通用。普通 feed 内 08:59 与 03:52 两种视频的按钮位置实测一致（1415 vs 1419）。
4. **倍速是粘性状态**：改了 2x 会一直保持到下一条视频，所以"松开恢复 1x"必须真的发 1.0x，不能省。
5. 实测中曾因菜单提前关闭导致点击落到视频上，feed 被切走一条（未点赞、未收藏、未改账号数据）；
   已把播放速度恢复到 1.0x 并用多条视频逐一确认。

### 8.10 动作层实现与限制（set_speed / seek_backward / seek_forward）

**实现方式**（xbox_douyin/douyin.py）：

| 方法 | 做法 | 依赖 |
| --- | --- | --- |
| seek_backward() | 发 speed.back_key（默认 "left"，支持 "a|b" 序列） | 只要抖音在前台，**不依赖画面状态** |
| seek_forward() | **零注入**，warning 日志说明"客户端没有前进 seek，按用户决定留空"，返回 False | 无 |
| set_speed(label) | 点 speed.button → 等 click_interval_ms → 点 speed.menu_y[档位] | 依赖两个坐标 + 菜单 hover |

set_speed 的关键细节（都是实测踩出来的）：

1. **两段连点，中间绝不移动光标**：
   优先调 injector.click_sequence([p1, p2], interval_ms, restore)（一次调用完成连点、中间不挪光标、末尾统一还原）；
   注入器没有该方法或签名不兼容时，退化成
   click_normalized(p1, restore=False) → sleep(interval) → click_normalized(p2, restore=True)。
   **第一次点击必须 restore=False**：否则光标被还原到原处，菜单因 hover 结束而关闭，第二次点击就落到视频画面上（= 播放/暂停）。
2. **间隔夹到 10~120ms**：实测菜单是 hover 层，超过 ~120ms 菜单可能已消失。
3. **粘性状态记忆（已修：未知初始态必须真点击）**：self._speed_label 记的是
   **"本进程成功点过的档位"**，不是"播放器当前状态"，**初始值是 None（未知）**，不是 "1x"。
   按数值归一化比较（"2x"/"2.0x"/"2X"/"2" 视为同一档）：
   * 记忆为 None（本进程还没点过）→ **任何请求都必须真发一次点击**，包括 set_speed("1x")；
   * 记忆等于目标档位 → 跳过点击、直接返回 True（优化只对本进程自己设过的档位生效）；
   * 点击成功才更新记忆；失败保持原值（失败后仍是 None/旧值）。
   为什么必须这么改：倍速是**粘性**的（跨视频保持），进程 A 把播放器点成 2x 后退出，
   进程 B 若把初始记忆假设成 "1x"，就会把 set_speed("1x") 判成"已经是 1x"而零注入返回 True ——
   那是**误报成功**，用户会一直卡在 2x。真机复现过，改后复验通过（见下面的跨进程真机确认）。
4. **返回值语义**：set_speed 返回 True 只表示**点击已经发出去了**，
   **不表示**"播放器速度已被验证"——动作层没有读数能力（Injector 不能读画面数值）。
   所以调用方不能把 True 当成"速度已切换成功"的证据，需要时用 tools/measure.py 截图核对标签。
5. **未知档位拒绝注入**：label 不在 speed.menu_y 里（例如 "0.5x"，菜单最低就是 0.75x）→ 返回 False，
   warning 日志列出可用档位，一个点击都不发。
**限制（无法自动判断，只能靠日志 + 复校）**：

* **直播房间没有倍速按钮**（底部条只有 连播 + 音量）。这时点 speed.button 会打到别的控件（附近是 连播 开关/音量）。
  现在由 §8.11 的守卫（Injector.sample_bright_ratio + speed.probe_roi/probe_min_ratio）先判定：
  采样低于阈值就**一个点击都不发**并返回 False。守卫默认 ROI 是右侧「收藏五角星」(0.9600,0.6591,0.9782,0.6915)，
  阈值 0.15（普通视频实测 ~0.30，暗背景直播间 ~0.068）；**亮背景直播仍会漏判**（实测 1.0000），
  所以产品上仍建议"只在普通视频上触发倍速"。
* **点完不校验结果**：客户端改版/换分辨率导致坐标漂移时，是"点了但没生效"，不会抛错。
  定期用 python tools/measure.py --report 核对"倍速按钮/菜单档位"的绝对像素是否还压在按钮上。
* **菜单 hover 依赖**：如果用户这时正好在动右摇杆（光标一直移动），连点会被打断；这是物理限制，已在日志里可追踪。

**真机确认（一次，2026-01 第三轮）**：用**真实 Injector + DouyinActions.set_speed** 做了一遍 1x → 2x → 1x，
读左下时间码（客户区 (205,872)-(310,906)）与底部条速率标签：

| 步骤 | 时间码 | 速率标签 | 说明 |
| --- | --- | --- | --- |
| 探测 0 | 01:19 / 04:13 | 1.0x | 起始 |
| 探测 +1.6s | 01:20 | 1.0x | 1x 基线（+1s） |
| set_speed("2x") 后 | 01:21 | **2.0x** | 标签已变 |
| +3s | 01:28 | 2.0x | **+7s / 约 3.3s ≈ 2.1x** |
| set_speed("1x") 后 | 01:29 | **1.0x** | 已恢复 |
| +3s | 01:32 | 1.0x | **+3s / 约 3.3s ≈ 1x** |

结论：set_speed 的"点按钮 + 点档位"在真机上确实把播放速率改成 2x 并能恢复 1x；
实测时 injector.py 已提供 click_sequence，所以真机走的是主路径（一次连点），退化路径由单测覆盖。

**跨进程真机确认（2026-01 第四轮，修粘性记忆用的）**：
进程 A 与进程 B 是**两个独立的 python 进程**，各自 _speed_label 初始都是 None：

| 进程 | 步骤 | 时间码 | 速率标签 | 判读 |
| --- | --- | --- | --- | --- |
| A (pid 2720) | 起始 | 00:24 / 09:17 | 1.0x | — |
| A | set_speed("2x") -> True，记忆 None→"2x" | 00:25 | **2.0x** | 真的点了 |
| A | +3s | 00:32 | 2.0x | **+7s / 约 3.3s ≈ 2.1x** |
| B (pid 33096，新进程) | 起始（记忆 None） | 00:35 / 09:17 | **2.0x** | 播放器确实是 2x |
| B | set_speed("1x") -> True，记忆 None→"1x" | 00:36 | **1.0x** | **新进程真的发起了点击** |
| B | +3s | 00:40 | 1.0x | **+4s / 约 3.4s ≈ 1x** |

这一轮之前的旧实现里，进程 B 因为初始记忆被假设成 "1x"，会零注入直接返回 True，标签停在 2.0x（Lead 真机复现）；
改成"初始 None + 未知必须真点击"后，进程 B 正常把速度恢复成 1.0x。
守卫采样值同时记录了：0.2922（右侧星形 ROI）>= 阈值 0.15，所以守卫放行。

**单测覆盖**（tests/test_douyin.py，共 31 个用例）：seek_backward 发配置键、seek_forward 零注入且返回 False、
set_speed 主路径只调一次 click_sequence 且两点为 (0.8600,0.9633)+(0.8618,0.8727)、
退化路径是 click_normalized(restore=False)+click_normalized(restore=True)、
**新实例请求 1x 必须有注入**、本进程设过 2x 后再请求 2x 才零注入、设过 2x 后请求 1x 必须真点且记忆变 1x、
注入失败记忆保持 None、"0.5x" 未知档位零注入 + 日志列出可用档位、间隔夹到 120ms，
外加 7 个守卫用例（None/低占比/高占比/异常/老注入器/已同档位零采样/新实例必须采样+点击）。

### 8.11 倍速守卫（只在普通视频上生效）实测与实现

动机：直播房间没有倍速按钮，点 (0.8600,0.9633)/(0.8618,0.8727) 会打到 连播 开关和弹幕/礼物区 —— 真金白银的风险。

**实现**（xbox_douyin/douyin.py）：set_speed() 在发点击前调用 Injector.sample_bright_ratio(speed.probe_roi)，
用"亮像素占比"判断是不是普通视频。**行为刻意不对称**（宁可功能可用，绝不误点直播间）：

| 采样结果 | 行为 | 日志 |
| --- | --- | --- |
| 注入器没有 sample_bright_ratio（老版本） | 跳过守卫，照常执行 | debug |
| 返回 None（窗口找不到/采样失败/异常） | 视为"未知"，照常执行 | info |
| 返回数值但 < probe_min_ratio | **阻断：一个点击都不发**，return False | warning |
| 返回数值且 >= probe_min_ratio | 执行 | debug |

粘性记忆命中（请求档位 == 上次成功档位）时**连采样都不做**，直接 return True。

#### 实测 1：现配置的 probe_roi = (0.1242, 0.9397, 0.1878, 0.9763)（底部时间码区），lum 阈值 160

用**真实 Injector.sample_bright_ratio** 采样（客户区 1651x928）：

| 场景 | 亮字占比 |
| --- | --- |
| 普通视频 #1 控制条亮 / 暗 | 0.0885 / **0.0000** |
| 普通视频 #2 控制条亮 / 暗 | 0.0992 / **0.0000** |
| 普通视频 #3 控制条亮 / 暗 | 0.1017 / **0.0000** |
| 另一轮 普通视频 #1 亮 / 暗 | 0.0000 / 0.0000 |
| 另一轮 普通视频 #2 亮 / 暗 | 0.0969 / 0.0980 |
| 另一轮 普通视频 #3 亮 / 暗 | 0.0275 / 0.0275 |
| 直播房间 #1 | **0.2230** |
| 直播房间 #2 | **0.0930** |

阈值扫描（同一口径复算，阈值 60/80/100/120/140/160/180/200/220 共 9 档）：普通视频控制条变暗后，
亮字占比从 100 档起恒为 0.0000；直播房间在 9 档上分别落在 0.0625~0.9922 与 0.0000~0.4185 ——
**与普通视频完全没有干净间隔**。

**结论：现配置这个 ROI + "低于阈值就算直播"的判据不可用，而且方向是反的：**
* 用户不动鼠标几秒后控制条会**淡出**（不是消失，是变暗），时间码亮度掉到阈值以下 → 普通视频读数 0.0000
  → 会被误判成"直播"而**阻断正常功能**（而这恰恰是最常见的状态）；
* 直播房间的时间码位置被**礼物栏**占据，反而常常更亮（0.0930 / 0.2230）→ 拦不住真正要拦的场景。

**因此建议把 probe_min_ratio 设为 0.0（守卫默认关闭）**，除非换 ROI（见实测 2）。
按现在的 0.02，用户只要几秒没动鼠标，倍速就会被自己人拦掉。

#### 实测 2：换 ROI 到右侧「收藏五角星」(0.9600, 0.6591, 0.9782, 0.6915)

> 下面"实测 1"保留的是最初配置（底部时间码区 + 0.02）的测量记录，用来说明那个判据为什么不可用。

| 场景 | 亮字占比 |

| 普通视频 #1 控制条亮 / 暗 | 0.3011 / 0.3011 |
| 普通视频 #2 控制条亮 / 暗 | 0.3011 / 0.3011 |
| 普通视频 #3 控制条亮 / 暗 | 0.3033 / 0.3089 |
| 直播房间 #1 | **0.0678** |
| 直播房间 #2 | **1.0000**（亮背景直播，ROI 被整片亮色覆盖） |

右侧按钮栏**不会随控制条淡出**（亮暗两态数值完全一致），所以不存在"误阻断普通视频"：
普通视频稳定在 0.30 左右，取 probe_min_ratio ≈ 0.15 时还有 2 倍余量。
但**亮背景的直播会漏判**（0.15 只拦得住暗背景直播间；直播 #2 读数 1.0000）。

**结论**：这是"单 ROI 亮像素占比"能做到的最好情况 ——
换 ROI 后**不会误伤普通视频**、能拦住一部分直播间，但**拦不全**。
若要真正可靠，需要 injector 更强的原语（任选其一）：
* sample_text_ratio(roi)：统计"很亮且 8 邻域很暗"的像素（即"黑底白字"）—— 时间码符合，礼物栏/亮背景不符合；
* 一次采多个薄 ROI：实测时间码区**上切片**（客户区 y872..882）普通视频 6/6 次都是 0.0000，
  直播 2/2 次是 0.0295 —— 能用，但方向是"高=直播"（与当前契约相反），且样本量太小，不宜直接定稿。

#### 单测（tests/test_douyin.py，31 个用例全绿）
* 采样 None → 照常执行，1 次 click_sequence，日志含"不可用"；
* 采样 probe_min_ratio/2（必然低于阈值）→ 返回 False，**0 次注入**，日志含"疑似直播房间"；
* 采样 probe_min_ratio*2（必然高于阈值）→ 执行，1 次 click_sequence；
* 守卫用的 ROI 就是 config 里的 probe_roi；
* 采样抛异常 → 不阻断（1 次注入）；
* 注入器没有采样原语（老版本）→ 不阻断（1 次注入）；
* 档位未变化（本进程已点成同档）→ 连采样都不做，零注入；
* 新实例请求 1x → 必须采样一次 + 真的点一次（不能因为"默认 1x"就跳过）。
（阈值随 config 走，测试里不硬编码常量，Lead 之后调 probe_min_ratio 不会让测试变脆。）

#### 已知盲区（无论用哪个 ROI）
1. **全屏/清屏模式**下右侧按钮栏和底部控制条都会隐藏 → 任何基于这两处的判据都会判成"非普通视频"而阻断
   （此时确实也没有倍速按钮，属可接受）。
2. **视频详情页**的底部控制条位置不同（客户区 y≈261），守卫可能判成"普通视频"放行，但点击坐标会落错 ——
   这是布局/坐标问题，守卫管不了。
3. 亮背景直播漏判（实测 1.0000），所以即便换 ROI，也建议保留"只在普通视频上触发"的产品约定。

### 8.12 评论开关（X 打开 / 再按一次关闭）

**问题**：抽屉打开后右侧按钮栏整体左移 419px（实测 0.9685 → 0.7145，掩码列 1598 → 1179），
再用"打开"的坐标点击会点进抽屉里的内容，所以关闭必须用另一个落点。

**实现**（xbox_douyin/douyin.py，方法名 open_comments 不变，做成开关）：

| 状态 | 动作 | 坐标来源 |
| --- | --- | --- |
| 未打开（_comments_open=False） | 点右侧评论气泡 | cfg.comments（0.9685, 0.5922） |
| 已打开（_comments_open=True） | 点抽屉右上角 × | cfg.comments_close（0.9830, 0.0863） |

* 关闭动作同样走 _run_action 分发 → 配置里把 comments_close 改成 method="key"（例如 esc）也支持。
* 点击失败/注入异常：状态**保持不变**并返回 False（没点成不算改了状态）。
* 状态复位（避免"抽屉早被关掉、记忆里还开着"→ 下次按 X 只点 × 没反应）：
  swipe_up / swipe_down 成功后复位；back 成功后复位；另提供 public 方法 reset_ui_state()
  一次清空所有 UI 状态记忆（外部事件后可调）。
* **不做亮度守卫**（评论入口对普通视频/直播都有意义），但也不依赖采样原语，老注入器照样能跑。
* 旧配置缺 comments_close 时回落到实测兜底 (0.9830, 0.0863)，不会掉到占位 (0.5, 0.5) 把点击打到视频中间。

**真机判据（本轮用的两个，读数完全一致）**：
1. 右侧「收藏五角星」ROI 的亮像素占比（Injector.sample_bright_ratio）：
   抽屉关闭 **0.2911 → 0.2922**；抽屉打开 **0.0000**（按钮栏左移，ROI 里只剩视频画面）。
2. 按钮栏「点赞心形」不变掩码列 x（老办法，3 帧不变+高亮的连通域质心）：
   抽屉关闭 **1598**；抽屉打开 **1179**（两者差 419px，与早期实测完全吻合）。

**真机结果（2026-01 第五轮，真实 Injector）**：

| 步骤 | open_comments() | _comments_open | 星形 ROI | 图标列 x | 判定 |
| --- | --- | --- | --- | --- | --- |
| 初始 | — | False | 0.2911 | 1271（该帧取到视频亮块，判据 1 为准） | 抽屉关闭 |
| 第一次按 X | True | True | **0.0000** | **1179** | **抽屉打开** ✓ |
| 第二次按 X | True | False | **0.2922** | **1598** | **抽屉关闭** ✓ |

截图核对：打开时右侧出现「详情 / TA的作品 / 评论 / AI抖音 / 相关推荐」抽屉与评论列表，× 就在 (0.9830, 0.0863)。

**已知风险**：直播房间的右侧不是这条竖排按钮栏（是弹幕/在线观众区），
所以 (0.9685, 0.5922) 在直播间未必是评论图标 —— 本轮没有在直播间真点（避免误触礼物/连播），
若要在直播间也支持评论开关，需要先量直播间的评论入口坐标。

### 8.13 双 ROI 守卫 + 竖屏版面（2026-01 第六轮）

#### 为什么要双 ROI
普通 feed 有两种版面：
* **横屏（多数）**：右侧按钮栏在客户区 x≈1598 → 归一化 0.9685，收藏星形在 (0.9685, 0.6753)；
* **竖屏（少数）**：按钮栏整条左移（实测一帧：x≈1399 → 0.8479），且整体下移约 69px。

只采横屏 ROI 时，竖屏视频会读到 0.0000 → 被守卫误判成"直播房间"，倍速直接失效。
所以守卫改成 **ratio = max(横屏 ROI, 竖屏 ROI)**：`probe_roi` = (0.9600,0.6591,0.9782,0.6915)，
`probe_roi_portrait` = (0.8310,0.6591,0.8492,0.6915)，`probe_min_ratio` = 0.15。

#### 版面判定（_layout_ratio，可在别处复用）
* 只有横屏 ROI ≥ 阈值 → **landscape**
* 只有竖屏 ROI ≥ 阈值 → **portrait**
* 两个都 ≥ 阈值 → **landscape**（宽屏才是已校准坐标的版面）
* 都不 ≥ 阈值 / 都拿不到 → **unknown**
* 任一 ROI 为 None → 只用另一个；两个都 None → 视为"未知"，按不对称策略放行

#### 守卫行为（不变的不对称策略）
| 情形 | 行为 |
| --- | --- |
| 注入器没有 sample_bright_ratio | 跳过守卫，照常执行（debug） |
| 横屏/竖屏都 None | 视为未知，照常执行（info） |
| max ≥ 阈值 | 执行（debug） |
| max < 阈值 | **阻断，零点击**（warning，日志里同时打出横屏/竖屏两个读数） |

#### 竖屏版面：评论 / 收藏整条跳过（安全侧 + 不猜坐标）
竖屏下按钮栏位移，原有 0.9685 坐标会点进视频画面 = 误触播放/暂停，比"没反应"更糟。
所以检测到 layout=portrait 时：
* open_comments() / favorite() → **一个点击都不发**，warning：竖屏版面：评论/收藏图标坐标尚未实测校准，已跳过（倍速仍可用），返回 False；
* 倍速**不受影响**（守卫已双 ROI，倍速按钮在底部条，与按钮栏无关）；
* 注入器没有采样能力（老版本）→ 判不出版面 → 照旧执行（向后兼容）。

#### 竖屏坐标：本轮没抓到实时帧，但用历史帧量到了候选值
按"最多滑 8 条"的规则扫了 8 条视频，读数如下（横屏 ROI / 竖屏 ROI）：

| 视频 | 横屏 ROI | 竖屏 ROI | 判定 |
| --- | --- | --- | --- |
| #1–#3 | 0.2911 / 0.3000 / 0.3000 | 0.0000 | 横屏 |
| #4 | 0.0889 | 0.0000 | 都不是（过渡帧/画面被遮） |
| #5–#8 | 0.2978 / 0.3111 / 0.3022 / 0.3033 | 0.0000 | 横屏 |

**8 条内没有竖屏帧 → 实时测量暂无法完成。**
不过上一轮我存过一帧真实竖屏帧（dyexp2/zz_final.png），把它解出像素重新做连通域后量到（客户区 1651×928）：

| 元素 | 客户区像素 | 归一化 | 与横屏的差 |
| --- | --- | --- | --- |
| 点赞心形 | (1399.1, 544.4) | **0.8479, 0.5872** | x −199px，y +69px |
| 评论气泡 | (1398.6, 618.0) | **0.8476, 0.6667** | x −199px，y +69px |
| 收藏五角星 | (1399.0, 694.7) | **0.8479, 0.7494** | x −199px，y +69px |

（三块 blob 的像素数 320/312/273 与横屏下的心形 324 / 评论 311 / 星形 265 一一对应，位置关系也自洽，可信度较高。
但这是**单帧、且是上一轮抓到的帧**，建议配置落地前再抓一帧实时竖屏核对一次；另外 y 下移量可能取决于视频宽高比。）

顺带印证：Lead 选的竖屏 ROI (0.8310..0.8492, 0.6591..0.6915) 在这一帧里正好压在**评论气泡** (1399, 618) 上，
所以竖屏时它读到高值是对的 —— 判"是普通视频"没问题，只是不能拿它当坐标用。

### 8.14 竖屏：先采样自证再点（2026-01 第七轮）

配置落地：comments_portrait = (0.8476, 0.6667)、favorite_portrait = (0.8479, 0.7494)
（§8.13 量出的单帧值，config 注释已注明"单帧实测、y 偏移可能随宽高比变化"）。

#### 新流程（layout == portrait 时）
1. 目标点 = 对应 portrait 坐标；
2. 以该点为中心采一个小 ROI 自证"图标确实在这儿"：
   半宽/半高 _PORTRAIT_PROBE_HALF = (0.0091, 0.0162) —— **由横屏星形 ROI 的一半得来**
   （横屏 ROI 0.9600..0.9782 宽 0.0182、0.6591..0.6915 高 0.0324，所以半宽 0.0091 半高 0.0162），
   这样竖屏采到的框与横屏图标框同尺寸，占比可以直接沿用 probe_min_ratio（横屏图标实测约 0.30）；
3. 占比 >= 阈值 → 点下去（评论仍走开关状态机）；< 阈值 / None / 无采样原语 → **零点击 + warning + False**。

#### 不对称策略（和倍速守卫相反，故意的）
| 场景 | 倍速守卫 | 竖屏评论/收藏 |
| --- | --- | --- |
| 采样不可用（无原语 / None） | **放行**（失败只是没加速） | **阻断**（点歪会落进视频画面 = 播放/暂停，比"没反应"更糟） |
| 采样命中但值很低 | 阻断 | 阻断 |

#### 竖屏下的"关闭"：选"不点 + 提示按 B"，并保持状态为 True
理由：
1. 竖屏抽屉的 × 没有实测坐标（横屏的 (0.9830, 0.0863) 在竖屏下是否仍落在 × 上未验证），
   按"不猜坐标"原则不去赌一次点击；
2. **不复位 _comments_open**：抽屉客观上还开着，写 False 就是撒谎；而且复位后下一次按 X 会走"打开"分支，
   虽然自证采样大概率会失败挡住，但依赖这种间接保护太脆；
3. 提示用户按 **B**，而 back() 成功后本来就会复位状态 —— 闭环成立；
4. 用户若自己用鼠标关掉，reset_ui_state() / 下一次切视频也会复位。

#### 单测（tests/test_douyin.py，共 52 个用例）
* 竖屏 + 自证命中 → 点击 **portrait 坐标**（并断言不是横屏坐标、采样框 = portrait_probe_roi(中心)）；
* 竖屏 + 自证低 → 评论/收藏都零点击、状态不变、warning 含"未对齐"；
* 竖屏 + 无采样原语 → 零点击（warning 含"没有采样能力"，绝不盲点竖屏坐标）；
* 竖屏 + 已打开 → 零点击、状态保持 True、warning 含"请按 B 键"，之后 back() 自动复位；
* 横屏回归：开 → 评论坐标、再按 → × 坐标、收藏 → 横屏收藏坐标（共 3 次点击全对）；
* 无采样原语的老注入器 → 横屏路径照旧执行（向后兼容）。

#### 真机（横屏，2026-01 第七轮）
| 步骤 | 读数 | 判定 |
| --- | --- | --- |
| 起始（先点一次 × 保证干净） | 横屏 ROI **0.2922**、竖屏 0.0000 | 抽屉关闭 |
| X 第一次 | open_comments() True，state True；横屏 ROI **0.0000**（抽屉盖住） | 抽屉打开 ✓ |
| X 第二次 | open_comments() True，state False；横屏 ROI 回到 **0.2922** | 抽屉关闭 ✓ |
| set_speed("2x") | True；底部标签 1.0x → **2.0x** | 倍速可用 ✓ |
| set_speed("1x") | True；底部标签 **1.0x** | 已恢复 ✓ |

**竖屏那条真机仍未验到**：本轮又扫了 5 条视频（期间评论抽屉被打开过，横屏 ROI 全是 0.0000；
之后换的几条也都是横屏版面），加上上一轮 8 条，累计 13 条里没有一帧竖屏版面。
所以竖屏"自证再点"只有单测覆盖 + §8.13 的单帧坐标 —— 发版时建议在 README 里注明：
"竖屏坐标来自单帧实测，若竖屏下评论/收藏没反应，用 tools/measure.py 复校并改 *_portrait"。
